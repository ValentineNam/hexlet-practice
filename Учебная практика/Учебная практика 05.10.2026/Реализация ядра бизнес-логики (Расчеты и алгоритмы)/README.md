# Реализация ядра бизнес-логики (Расчеты и алгоритмы)

## Единая реализация

- `discount.py` — скидка по суммарному количеству проданных единиц. Формула предыдущей практики сохранена без изменений.
- `material_calculator.py` — единственная реализация расчета материалов; интерфейс из пяти аргументов сохранен.
- `material_catalogs.py` — параметризованное чтение коэффициентов и списка справочников из PostgreSQL.
- `database.py` — подключение ядра и финального backend к схеме `practice_2026_10_05`.
- `demo_catalogs.py` — только исходные демонстрационные значения для ETL, не источник данных работающего калькулятора.

Копии алгоритмов в заданиях UI и аудита удалены. Backend импортирует модули из этой папки; аудит запускает эти же unit-тесты через `test_core_*`, без коллизий одинаковых имен модулей.

## Скидки

| Общее количество за все время | Скидка |
|---|---|
| < 10000 | 0% |
| 10000–49999 | 5% |
| 50000–299999 | 10% |
| ≥ 300000 | 15% |

`server.list_partners()` использует `LEFT JOIN sales_history`, `SUM(quantity)` и `COALESCE(..., 0)`, затем вызывает `calculate_partner_discount`. Партнер без продаж остается в реестре со скидкой 0%. Денежная сумма продажи на скидку не влияет.

## Расчет материалов

```python
calculate_material_requirement(product_type_id, material_type_id, quantity, param_1, param_2)
```

Формула: `ceil(quantity × param_1 × param_2 × coefficient × (1 + scrap_percentage / 100))`.

Коэффициенты запрашиваются при каждом корректном вызове из `product_types` и `material_types`. Изменение справочника сразу влияет на расчет. Неизвестный ID, неположительное количество/параметры, неверные типы, NaN и бесконечности возвращают `-1`. Некорректные входные данные отсекаются до обращения к БД. Параметры допускают `int`, `float` и `Decimal`; для точного десятичного ввода предпочтителен `Decimal`.

Вычисление использует Decimal и локальную точность, рассчитанную по операндам, чтобы не потерять дробный хвост перед округлением вверх. Полученное целое число не увеличивается, если расход уже целый.

Ошибки подключения/отсутствия таблиц вызывают `CatalogUnavailableError`, а не маскируются под `-1` и не включают fallback на словари. Пустой список справочников — также явная ошибка загрузки. Отдельная отсутствующая запись при расчете дает `-1`.

## Интеграция и настройка

Используйте существующий интерпретатор с `psycopg2` и `python-dotenv` (те же зависимости, что у UI и ETL). Установки новых библиотек не требуется.

Перед рабочим запуском выполните согласованный ETL задания 1. Настройки читаются при подключении: переменные процесса → локальный `.env` задания UI → `.env` задания ETL. Старые практики для работы ядра и backend не используются. `DB_SCHEMA` допускается только `practice_2026_10_05`. Не запускайте приложение с параметрами рабочей БД для интеграционных тестов.

`GET /api/material/catalogs` возвращает значения из БД (включая происхождение `demo`/`customer`). `POST /api/material/calculate` вызывает эту же функцию:

- 200 и `material_requirement` — число или `-1` для неверных значений;
- 400 — ошибочный JSON/отсутствие обязательных полей;
- 503 — недоступны БД/таблицы справочников.

UI отправляет параметры размеров десятичными строками, чтобы JavaScript Number не терял точность ввода. API преобразует их в Decimal; JSON-числа размеров также читаются как Decimal. Числовые строки принимает только API на границе ввода; сама функция по-прежнему отвергает строки. Формат ответа и пять полей запроса сохранены.

При исходных демонстрационных значениях из БД `(1, 2, 100, 1, 1)` дает `126`. Эти значения помечены `demo`, а не выдаются за коэффициенты заказчика.

## Тесты без PostgreSQL

Из этой папки:

```bash
python3 -B -m unittest discover -s . -v
```

16 unit-тестов проверяют пороги скидки, валидацию, неизвестные ID, округление и сохранение десятичного хвоста, SQL-параметризацию, закрытие соединения и ошибки справочников. PostgreSQL-сценарии по умолчанию пропускаются. Unit-тесты явно подменяют источник коэффициентов; рабочее приложение этого не делает.

## Изолированная интеграционная проверка

Используется сохраненный кластер этапа 1: `/private/tmp/stage1-etl.bxjg75/data`, Unix-сокет `/private/tmp/stage1-etl.bxjg75`, порт 55435, БД `stage1_etl_test`. TCP PostgreSQL отключен.

После отдельного разрешения и запуска этого кластера:

```bash
STAGE2_ALLOW_DB_WRITE=1 STAGE2_TEST_DSN='host=/private/tmp/stage1-etl.bxjg75 port=55435 dbname=stage1_etl_test user=v.nam' python3 -B -m unittest discover -s . -v
```

До любых записей тест сверяет имя БД, реальный `data_directory` и отключенный TCP. Для HTTP поднимается временный сервер на loopback и свободном порту. Тестовые изменения выполняются в транзакциях с откатом, затем сравниваются все записи пяти таблиц с состоянием до теста. Схема этапа 1 и исходные пользовательские тестовые записи сохраняются.

Проверены 7 сценариев PostgreSQL + HTTP: изменение коэффициентов (результат 126 → 220), штатное подключение ядра, неизвестные/удаленные записи, пустые справочники/отсутствующие таблицы, реальная ошибка подключения к отсутствующему тестовому сокету, точный десятичный ввод, агрегирование нескольких продаж на порогах скидки и партнер без продаж. HTTP-коды 200/400/503 проверяются автоматически.

Результат 10.10.2026: 23 теста прошли (16 unit + 7 интеграционных). Ошибки 503 и соответствующие stack trace в журнале ожидаемы в негативных сценариях. Визуальная проверка в браузере и нагрузочное тестирование не выполнялись.
