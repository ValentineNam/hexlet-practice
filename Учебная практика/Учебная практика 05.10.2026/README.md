# Учебная практика 05.10.2026

Четыре этапа используют общее Python-окружение: ETL и 3NF-хранилище, бизнес-логика, веб-приложение и аудит. Для запуска не нужны DEV, файлы переписок и окружения предыдущих практик. CSV включены в `Инфраструктура данных и ETL (База данных в 3NF)/raw`.

## 1. Установка после клонирования

Требуется Python 3.11+ с `venv` и `pip` (проверено на Python 3.13). Команды bash/zsh для macOS/Linux, **из корня клонированного репозитория**:

```bash
cd 'Учебная практика/Учебная практика 05.10.2026'
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip check
```

Окружение создаётся один раз в корне этой практики, не внутри задания UI. Нужен доступ к индексу пакетов для установки. Если ваша Linux-система не включает `venv`/`pip`, установите соответствующий пакет Python средствами ОС, затем повторите команды. Не используйте `sudo pip`.

Единственный список зависимостей — `requirements.txt`: `psycopg2-binary` (импортируется как `psycopg2`) и `python-dotenv` (как `dotenv`). Версии зафиксированы по проверенному окружению. Старые файлы `requirements.txt` этапов 1, 3 и 4 содержат только `-r ../requirements.txt` для совместимости. Отдельных тестовых Python-зависимостей нет: используется `unittest`.

Активация не обязательна: все инструкции явно вызывают Python из общего окружения. Команда системного `python3` не начинает видеть пакеты из `.venv` автоматически. Поэтому `--check-only` также нужно запускать правильным интерпретатором.

Для Windows PowerShell из корня репозитория:

```powershell
Set-Location 'Учебная практика/Учебная практика 05.10.2026'
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
```

В командах README этапов заменяйте `../.venv/bin/python` на `..\.venv\Scripts\python.exe`; путь для установки `../requirements.txt` остаётся относительным. Windows автоматически не проверялась. Для live-проверок PowerShell: `$env:FINAL_AUDIT_LIVE='1'`, затем запуск соответствующего тестового модуля и `Remove-Item Env:FINAL_AUDIT_LIVE` после проверки. Браузерный и исторические интеграционные сценарии имеют отдельные ограничения ОС, описанные в этапах 2 и 4.

## 2. Проверки без PostgreSQL

Каждый блок выполняется **из каталога указанного этапа**, после установки общих зависимостей:

| Этап | Команда | Ожидаемый результат |
|---|---|---|
| `Инфраструктура данных и ETL (База данных в 3NF)` | `../.venv/bin/python -B etl.py --check-only` | Преобразование CSV: 5 партнёров, 3 товара, 5 продаж, 1 отклонение; без подключения и записи отчёта |
| Там же | `../.venv/bin/python -B -m unittest discover -s tests -v` | 22 успешно, 1 пропуск |
| `Реализация ядра бизнес-логики (Расчеты и алгоритмы)` | `../.venv/bin/python -B -m unittest discover -s . -v` | 16 успешно, 7 пропусков |
| `Разработка UI, навигации и CRUD-форм` | `../.venv/bin/python -B -m unittest discover -s tests -v` | 7 успешно |
| `Автоматизированное тестирование, аудит безопасности и UX` | `../.venv/bin/python -B -m unittest discover -s . -p 'test_*.py' -v` | 27 успешно, 3 пропуска |

Не задавайте `STAGE1_ALLOW_DB_WRITE`, `STAGE2_ALLOW_DB_WRITE` и `FINAL_AUDIT_LIVE` для обычного запуска. Пропуски намеренные: они требуют отдельно подготовленной БД или работающего приложения. HTTP-тестам нужен доступ к локальному listening socket, но не PostgreSQL.

## 3. PostgreSQL и первоначальный импорт

Для полноценного приложения отдельно установите/запустите PostgreSQL и клиент `psql`. Python-пакет `psycopg2-binary` не устанавливает сервер. Роль должна иметь право подключаться к выбранной учебной БД и создавать в ней схему/таблицы. Импорт создаёт схему `practice_2026_10_05`, но **не саму БД**.

На своей новой учебной установке создайте БД один раз, если её ещё нет. Пример из любой директории (роль `postgres`, localhost и порт 5432 замените на свои):

```bash
createdb -h localhost -p 5432 -U postgres -W practice_2026_autumn
```

Не пересоздавайте существующую БД. В каталоге этапа 1 выполните:

```bash
cp -n .env.example .env
```

В PowerShell копирование без перезаписи: `if (!(Test-Path .env)) { Copy-Item .env.example .env }`.
Откройте `.env` в редакторе, заполните `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, оставьте `DB_SCHEMA=practice_2026_10_05`. Все значения должны относиться к вашей учебной БД. Переменные процесса имеют приоритет; проверьте, что в терминале нет посторонних `DB_*`.

Из каталога этапа 1 запустите импорт, который изменяет выбранную учебную БД:

```bash
../.venv/bin/python -B etl.py
```

Повторный импорт согласован с проверками: совпадающие данные пропускаются, конфликт приводит к откату, пользовательские данные не удаляются. Подробности и независимый SQL-аудит — в README этапа 1. Исторический fallback ETL на `.env` старой практики сохраняется в коде; полностью заполненный локальный `.env` устраняет зависимость от него.

## 4. Приложение и проверки с БД

Из каталога `Разработка UI, навигации и CRUD-форм`:

```bash
../.venv/bin/python -B server.py
```

Откройте `http://127.0.0.1:8010/index.html`. Остановка — Ctrl+C. Backend использует `.env` этапа 1, если в каталоге UI нет собственного `.env`; второй файл для первого запуска не нужен. Если файл UI существует, он имеет приоритет и должен указывать на ту же БД.

Из каталога этапа 4, при запущенном приложении на порту 8010:

```bash
FINAL_AUDIT_LIVE=1 ../.venv/bin/python -B -m unittest test_live_readonly -v
```

Эти три проверки только читают данные и вызывают калькулятор; ожидают исходные demo-справочники и результат 126. Они не настраивают БД и не записывают партнёров. Unit-тесты и настоящий запуск приложения — разные режимы; установка Python-зависимостей нужна обоим.

Исторические интеграционные тесты этапов 1/2 с записью не являются универсальным сценарием установки: их ограничения кластера зафиксированы в тестах. Подробности — в README этих этапов. Тестовые ожидания в ходе аудита воспроизводимости не менялись.

Общие правила репозитория и `.gitignore` этой практики исключают виртуальные окружения, `.env` (кроме шаблонов `.env.example`), кэш Python, журналы и временные файлы. Отчёт ETL `etl_rejections.csv` исключён в этапе 1. Настройки и секреты не включайте в коммит.

## 6. Проверка воспроизводимости 11.10.2026

Проверено на macOS arm64 / Python 3.13 в отдельной временной копии отслеживаемых файлов этой практики, без `.env`, DEV и прежних окружений. Создан новый `.venv`, оба пакета скачаны из индекса pip, `pip check` не обнаружил конфликтов. Проверены также относительные ссылки трёх файлов зависимостей этапов на общий список.

`etl.py --check-only` завершился успешно (5/3/5 и одно ожидаемое отклонение). Четыре набора тестов дали 72 успешных выполнения, 0 ошибок, 11 ожидаемых пропусков; повторно подключаемые тесты ядра входят в это число. Сервер запущен из новой копии: главная страница вернула HTTP 200, при намеренно несуществующем сокете PostgreSQL справочники вернули корректный HTTP 503. Рабочая БД не использовалась.

Первую загрузку пакетов блокировала сетевая песочница; после разрешения сетевого доступа установка прошла. Свежий импорт в PostgreSQL, live-сценарии и браузер в этом аудите установки не запускались. Windows/Linux автоматически не проверены. Исторические интеграционные сценарии с привязкой к прежнему кластеру остаются отдельным ограничением; изменения их ожиданий не выполнялись.
